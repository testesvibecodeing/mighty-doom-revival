O caminho completo, do zero até jogar

Este guia segue exatamente os scripts do repositório, na ordem em que eles devem rodar: baixar e validar o APK, preparar as ferramentas, subir o servidor Revival, colocá-lo em produção com HTTPS, gerar o APK patchado e instalar no celular. Nenhuma etapa aqui distribui o APK oficial — você usa a sua própria cópia.

01

Baixar e validar o APK

Você precisa da sua própria cópia do Mighty DOOM 1.13.1. O repositório não redistribui o APK — o link abaixo abre a página oficial da Uptodown numa aba nova, para você baixar por conta própria.

Abrir página de download da Uptodown ↗

Na aba que abriu

  1. Clique em Download.
  2. Se aparecer um desafio da Cloudflare (Turnstile), resolva-o normalmente — a Uptodown passou a exigir isso antes de liberar o link direto.
  3. Deixe o download terminar no navegador.

Agora coloque o arquivo na pasta input

Pegue o .apk baixado e coloque (ou mova) dentro da pasta do projeto, exatamente neste caminho:

caminho esperado
input/mighty-doom.apk

Se a pasta input ainda não existir, crie-a na raiz do projeto.

Rode a validação

Este comando confere o SHA-256 do arquivo contra o hash oficial alvo, recusa o arquivo se não bater, e gera o relatório de análise. Se o APK já estiver em input/ (como no passo acima), ele valida o que já está lá; se não estiver, ele tenta baixar sozinho.

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
scripts\analyze-official-apk.bat
./scripts/analyze-official-apk.sh
Se a Uptodown bloquear o download automático

O desafio Cloudflare às vezes impede o script de raspar a página sozinho. Solução manual: na aba que você abriu, depois de clicar em Download, copie a URL final que começa com https://dw.uptodown.com/dwn/... (aba Rede do DevTools do navegador, ou o gerenciador de downloads) e rode de novo passando essa URL:

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
scripts\analyze-official-apk.bat "https://dw.uptodown.com/dwn/..."
./scripts/analyze-official-apk.sh "https://dw.uptodown.com/dwn/..."

O que fica pronto

input/mighty-doom.apkcópia local validada, nunca vai para o Git
reports/apk-1.13.1.jsonrelatório sanitizado (hash, estrutura Unity/IL2CPP, endpoints conhecidos)
reports/apk-1.13.1.mdmesmo relatório em Markdown

02

Preparar as ferramentas do patcher

Baixa o apktool 3.0.3 e o uber-apk-signer 1.3.0 para a pasta .tools/ (fora do Git), conferindo o SHA-256 de cada um antes de aceitar o arquivo.

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
scripts\setup-patcher-tools.bat
./scripts/setup-patcher-tools.sh
Opcional

O patcher da etapa 05 chama este script sozinho se as ferramentas ainda não existirem. Rodar aqui antes só adianta o download e confirma que Java está corretamente instalado.

03

Subir o servidor Revival localmente

Use isto para testar o backend no seu próprio PC antes de colocar em produção. O celular não vai conseguir falar com 127.0.0.1 da sua máquina — para jogar de verdade, siga também a etapa 04.

Preparar

Copia server/.env e os config/*.json a partir dos .example, confere se o Node instalado tem node:sqlite funcional e roda um teste real end-to-end.

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
scripts\setup-server.bat
./scripts/setup-server.sh
Importante

Abra server/.env e troque REVIVAL_ADMIN_TOKEN=change-me por um valor seu — esse token autoriza recarregar a configuração do servidor.

Iniciar

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
scripts\start-server.bat
./scripts/start-server.sh

Health check local: http://127.0.0.1:8080/revival/health

GameData

Se server/data/game-data.json ainda não existir, o servidor tenta importar um snapshot comunitário automaticamente. Para rodar isso manualmente:

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
python scripts\fetch-community-gamedata.py
python3 scripts/fetch-community-gamedata.py
04

Deploy em produção (VPS com HTTPS)

O Android só conversa com o Revival Server por HTTPS público de verdade. Esta etapa roda inteira dentro de uma VPS Linux, não no seu PC.

Antes de começar, tenha em mãos

  • uma VPS Ubuntu 22.04+ (ou Debian) com acesso root/sudo;
  • um domínio ou subdomínio com registro DNS A apontando para o IP público da VPS (ex.: d.seudominio.com.br);
  • as portas 80 e 443 liberadas no firewall do provedor (security group) além do ufw.

Instalar (primeira vez, dentro da VPS)

bash na VPS (sempre Linux)
sudo apt-get update && sudo apt-get install -y git
git clone https://github.com/testesvibecodeing/mighty-doom-revival.git
cd mighty-doom-revival
sudo ./scripts/install.sh

O script pergunta o domínio HTTPS. Para rodar sem prompt interativo, informe-o antes:

bash na VPS
DOMAIN=d.seudominio.com.br sudo -E ./scripts/install.sh

O que ele faz sozinho

  • instala Node.js 24 LTS e o Caddy, se ainda não existirem;
  • prepara server/.env e os config/*.json a partir dos .example;
  • roda a suíte de testes do servidor como gate de deploy — aborta se algo quebrar;
  • sobe o servidor como serviço systemd, com reinício automático;
  • configura o Caddy como reverse proxy com HTTPS automático (Let's Encrypt) para o domínio informado;
  • valida http://127.0.0.1:8080/revival/health e depois https://SEU_DOMINIO/revival/health antes de terminar.
VPS compartilhada

Se Node.js e/ou Caddy já estiverem instalados nesta VPS (por outro projeto, por exemplo), o instalador nunca os reinstala nem passa a considerá-los deste projeto. Ele também nunca sobrescreve /etc/caddy/Caddyfile: só acrescenta a linha import (se faltar) e escreve o domínio deste projeto em um arquivo próprio dentro de /etc/caddy/conf.d/, sem tocar em outros domínios já configurados. Cada decisão fica registrada em deploy/.install-state e explicada com o prefixo [OWNERSHIP] no log da execução.

Ao final

Ele imprime o REVIVAL_ADMIN_TOKEN gerado — guarde-o. Também mostra os comandos para inspecionar os serviços:

bash na VPS
systemctl status mighty-doom-revival
systemctl status caddy
journalctl -u mighty-doom-revival -f

Atualizar depois de mudanças no código

bash na VPS
cd mighty-doom-revival
git pull
sudo ./scripts/install.sh

É idempotente — pode rodar de novo a cada git pull.

Desinstalar

O par do instalador, scripts/uninstall.sh, remove só o que pertence a este projeto (o serviço systemd e o site próprio do Caddy). Ele nunca apaga /etc/caddy/Caddyfile nem blocos de outros domínios/projetos que já estejam configurados nele.

bash na VPS
sudo ./scripts/uninstall.sh

Ele mostra o que vai (e o que não vai) ser removido e pede confirmação (-y pula o prompt). Por padrão preserva Node.js, Caddy e os arquivos locais (server/.env, server/data/, server/runtime/), mesmo os que o instalador tenha criado. Duas flags liberam uma limpeza mais completa:

bash na VPS
sudo ./scripts/uninstall.sh --purge-packages  # remove Node.js/Caddy, só se instalados por este projeto
sudo ./scripts/uninstall.sh --purge-data      # apaga server/.env, config, data/ e runtime/ (progresso incluso)
Atenção

--purge-packages só remove Node.js/Caddy se deploy/.install-state confirmar que foram instalados por este instalador — se já existiam antes (ou há outros sites em /etc/caddy/conf.d/), ficam preservados mesmo com a flag. --purge-data apaga o banco de progresso dos jogadores; use só se quiser mesmo zerar tudo.

05

Gerar o APK do Revival

Agora, de volta ao seu PC: esta etapa injeta o domínio do seu servidor (etapa 04) dentro do APK validado (etapa 01), reconstrói e assina uma cópia local.

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
scripts\patch-apk.bat
./scripts/patch-apk.sh

O assistente pergunta três coisas

Caminho do APKEnter aceita o padrão input/mighty-doom.apk
Hostname HTTPS do servidoro domínio configurado na etapa 04, ex.: d.seudominio.com.br
CA PEM/CRT localdeixe vazio — o caso normal, com certificado público Let's Encrypt do deploy em VPS

O que acontece por baixo

preflight HTTPS→ analisar APK→ desmontar→ aplicar servidor/TLS→ reconstruir→ verificar endpoint→ assinar→ cópia final

Resultado: output/mighty-doom-revival.apk (ignorado pelo Git).

Se parar em "needs_bundle_aware_patch"

Não é um bug: o patcher se recusa a corromper um bundle Unity trocando um hostname por outro de tamanho diferente sem uma reserialização segura. Detalhes em work/apk-patch/patch-report.json.

Se parar no preflight

O patcher exige que /revival/health já responda com o client 1.13.1, a API 24.0.0 e o GameData carregado antes de gerar qualquer APK. Volte à etapa 04 e confirme que o domínio está mesmo no ar em HTTPS.

06

Instalar no Android

  1. Nas configurações do Android, habilite Instalar apps desconhecidos para o app que você vai usar para abrir o APK (gerenciador de arquivos, navegador, etc.).
  2. Se o Mighty DOOM oficial já estiver instalado, desinstale-o primeiro — a assinatura do APK gerado é diferente (chave de laboratório própria do patcher), então o Android recusa atualizar por cima.
Atenção

Desinstalar o app oficial apaga os dados locais dele. Faça backup antes se houver progresso que você queira manter.

Com ADB (mais rápido, via cabo)

C:\mighty-doom-revival> ~/mighty-doom-revival$ 
adb uninstall com.bethsoft.ubu
adb install output\mighty-doom-revival.apk
adb uninstall com.bethsoft.ubu
adb install output/mighty-doom-revival.apk

Sem ADB

Copie output/mighty-doom-revival.apk para o celular (cabo, nuvem, etc.) e toque no arquivo pelo gerenciador de arquivos do Android para instalar.

Abra o app

Ele deve se conectar em https://SEU_DOMINIO — o servidor Revival que você subiu na etapa 04, e não mais os servidores oficiais.

Problemas comuns

SintomaCausa provávelO que fazer
Download automático falha na etapa 01 Cloudflare Turnstile bloqueando a raspagem da página baixe manualmente pelo navegador e passe a URL final dw.uptodown.com/dwn/... como argumento

App instala mas não conecta servidor sem HTTPS público válido, ou versão oficial não foi desinstalada antes revalide a etapa 04 (health check público) e repita a etapa 06
game_data_loaded: false no health check server/data/game-data.json ausente na VPS rode python3 scripts/fetch-community-gamedata.py na VPS e reinicie: sudo systemctl restart mighty-doom-revival
